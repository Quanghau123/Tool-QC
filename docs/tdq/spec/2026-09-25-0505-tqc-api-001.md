## 1. Mục tiêu & phạm vi
- Mục tiêu: mở rộng shared Redis transport của Tool-QC để đọc callback từ Redis Stream `BookingCampaignCreateStatusMessage`, correlate đúng `CampaignId` và `IdempotencyKey`, xác nhận `Status = 1`, rồi lưu `MtcNewsletterId` cho các bước lifecycle tiếp theo của testcase.
- Trong phạm vi:
  - Bổ sung thao tác đọc/chờ Redis Stream tổng quát vào shared contract, executor và preflight validator để mọi project chỉ cần khai báo key/group/consumer/payload/filter trong cấu hình hoặc testcase là sử dụng được.
  - Dùng key đầy đủ `${REDIS_STREAM_PREFIX}stream:${REDIS_MTC_CREATE_STATUS_STREAM}`, mặc định local tương ứng `sb_hau:stream:BookingCampaignCreateStatusMessage`.
  - Dùng consumer group riêng của Tool-QC, mặc định `tool-qc-be-booking`; không dùng chung group nghiệp vụ `sb-booking-hau`.
  - Parse field envelope `payload`, lọc callback bằng `CampaignId`, `IdempotencyKey`, `Status`, và trả JSON payload để cơ chế `save` lấy `$.MtcNewsletterId`.
  - Bổ sung các biến cấu hình Redis Stream dạng placeholder vào `.env.example` và `projects/be-booking/.env.example`; thêm key vào `.env` local nếu đang thiếu nhưng không in hoặc ghi đè secret hiện có.
  - Cập nhật đúng testcase `projects/be-booking/testcases/campaign/frozen-frame-duration-insertion-flow.json` để lấy `MtcNewsletterId` từ stream MTC; giữ PostgreSQL làm bằng chứng integrity riêng thay vì nguồn chính của ID.
  - Thêm unit/framework tests, chạy preflight, build và runtime đúng testcase destructive.
- NGOÀI phạm vi:
  - Không sửa backend Booking/MTC, Redis server, schema PostgreSQL hoặc format message hiện tại.
  - Không dùng consumer group `sb-booking-hau`, không ACK/xóa message thay mặt worker nghiệp vụ.
  - Không mở rộng sang Pub/Sub, Kafka, RabbitMQ, DLQ redrive hoặc auto-claim message của consumer khác.
  - Không sửa testcase khác ngoài các fixture/test framework cần chứng minh tính reusable của Redis Stream transport.

## 3. Cách tiếp cận & lý do
- Chọn: thêm một Redis command khai báo dạng `xreadgroup` vào transport hiện có. Executor tạo group Tool-QC nếu chưa tồn tại, bắt đầu ở vị trí chỉ nhận message mới phù hợp với testcase, đọc theo batch/retry, parse field `payload`, lọc các JSON path/value đã khai báo, và trả payload JSON gốc để assertion/save dùng chung cơ chế hiện có.
- Chọn: consumer group riêng `tool-qc-be-booking` và consumer duy nhất theo `${unique}`; không chia sẻ group với worker SB.
- Chọn: chỉ ACK entry đã match và được testcase chấp nhận trong group Tool-QC. Entry không match không được xóa khỏi stream; group Tool-QC không ảnh hưởng pending list của group nghiệp vụ.
- Chọn: testcase correlate đủ `CampaignId = ${campaignAId}`, `IdempotencyKey = ${dispatchIdempotencyKey}`, `Status = 1`; sau đó save `MtcNewsletterId` trực tiếp từ callback.
- Vì: Redis callback là nguồn contract trực tiếp của lifecycle SB ← MTC và đã chứa chính xác ID cần dùng; query PostgreSQL trước đây có thể khóa nhầm/không thấy transaction theo timing.
- Đã loại: dùng chung group `sb-booking-hau` — có nguy cơ tranh message với worker nghiệp vụ.
- Đã loại: chỉ `XRANGE` toàn stream — dễ đọc lại callback cũ và tăng chi phí theo độ dài stream; group riêng kiểm soát cursor tốt hơn.
- Đã loại: bỏ kiểm tra PostgreSQL — mất evidence integrity; bước DB được giữ nhưng chạy sau khi lấy ID từ stream.

## 4. Yêu cầu bắt buộc
- Log service bật mặc định: báo stream key, group, consumer, số entry đã đọc và lý do bỏ qua ở mức không lộ payload/secret; có thể giảm qua cấu hình log hiện hữu.
- Không placeholder, TODO stub hoặc mock trình bày như dữ liệu runtime thật.
- Không in connection string, token hoặc toàn bộ `.env`; chỉ kiểm tra/tạo tên key cấu hình.
- Mỗi thành phần contract, executor và validator phải có kiểm thử tương ứng.
- Code C# bám style hiện tại, SOLID, không nhúng tên project, stream hoặc message nghiệp vụ vào shared executor; project mới chỉ cần cấu hình dữ liệu để dùng Redis Stream.
- Redis Stream filter phải là dữ liệu testcase, không hard-code `CampaignId`, `IdempotencyKey`, `Status` trong framework.
- Timeout/cancellation phải được tôn trọng; không để process treo vô hạn.

## 5. Ràng buộc & rủi ro
Ràng buộc kiến trúc phải giữ:
- `Testcase project: khai báo request, fixture, assertion và coverage cho từng dịch vụ.` — testcase khai báo stream/filter/save, không chứa code thực thi.
- `Shared runner: đọc schema, nội suy biến, thực thi transport và sinh report.` — Redis executor là capability dùng chung, không chứa business rule MTC.
- `Shared runner không được chứa business rule riêng của be-booking hoặc MTC.` — mọi stream name, prefix, group và filter đi qua config/testcase.
- `QC chỉ đọc backend source và dữ liệu runtime; không sửa backend PROD trong request này.` — chỉ thay Tool-QC.

| Rủi ro | Ảnh hưởng | Cách giảm |
|---|---|---|
| Group tạo sau khi callback đã publish | Bỏ lỡ message | Testcase phải khởi tạo/capture cursor trước thời điểm kích hoạt dispatch hoặc chọn group start semantics rõ ràng và có unit test. |
| ACK nhầm message | Mất evidence trong group Tool-QC | Chỉ ACK entry match đầy đủ; không dùng group nghiệp vụ; không XDEL. |
| Message không match tích tụ pending | Pending list group Tool-QC tăng | Đọc new messages theo batch, ghi chẩn đoán; không claim group khác; thiết kế cleanup/group lifecycle có giới hạn rõ. |
| Payload field/casing thay đổi | Không parse/save được | `payloadField` cấu hình được; JSON path match không phân biệt business naming nhưng path testcase rõ ràng. |
| Retry đọc trùng callback | Save nhầm/lặp | Correlate campaign + idempotency + status và ACK entry match sau khi parse thành công. |
| `.env` có secret | Rò rỉ cấu hình | Chỉ thêm key thiếu, không đọc/in giá trị; `.env.example` dùng placeholder. |
| Shared contract gây regression | Testcase Redis cũ hỏng | Giữ tương thích constructor/default; chạy framework tests và build solution. |
